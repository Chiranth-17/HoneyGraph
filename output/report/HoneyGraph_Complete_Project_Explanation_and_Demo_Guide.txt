2. The problem and our objectives
Explain the need before discussing the tools

Problem statement in simple language

An IoT network may contain cameras, energy meters, traffic controllers and environmental sensors. Every device can produce many small activity records. Looking at each record separately makes it difficult to notice repeated login failures, unusual traffic or activity moving between devices.

A security analyst needs to answer: What happened? Which device was affected? Which rule detected it? How are different findings connected? Can we trust the stored evidence?

SAY: The problem is not just collecting logs. We need to turn many separate observations into a clear investigation, while preserving links back to the evidence.

Project objectives

1. Generate realistic but safe activity for about 500 virtual IoT devices.
2. Store structured events and reject records that do not follow the schema.
3. Detect suspicious patterns using editable MongoDB aggregation rules.
4. Connect related alerts into incidents and ordered multi-hop chains.
5. Calculate device risk and find affected devices near a location.
6. Detect changes, missing records and reordering in per-device log chains.
7. Provide a role-aware dashboard backed by real database permissions.

What makes the project a DBMS project?

The database performs useful work: filtering and grouping events, notifying workers about inserts, traversing alert relationships, enforcing validation, committing related writes, locating nearby devices and expiring old data. Python coordinates these database operations; React presents the results.

A simple Mirai-style story

SAY: A simulated source scans a device, tries several passwords, records a successful login and then command activity. These observations become events. Detection rules identify suspicious patterns and create alerts. Related alerts are grouped into an incident, so the analyst can understand the sequence.

A normal event does not automatically become an alert. An alert does not automatically prove a real compromise. The incident graph summarizes related observations; the underlying events remain the supporting evidence.

6. How an event enters the system
Validation, ordering and hash chaining

1. The simulator sends one event or a batch to POST /api/ingest. A batch can contain up to 5,000 events.
2. Pydantic validates the request before storage. MongoDB strict JSON Schema validation checks the stored document again.
3. The ingestion service finds each device chain head and serializes concurrent writes for that device.
4. It assigns prevHash, hash, chainSeq, eventInsertedAt and an ingestBatchId.
5. An unordered bulk insert runs inside a transaction. A failed batch aborts; the in-memory head stays at the last confirmed state.

hash = SHA256(prevHash + canonical_event_json)
Genesis prevHash = 64 zero characters

The canonical data contains ts, deviceId, protocol, eventType, srcIp, geo and payload. Keys are sorted, unnecessary spaces are removed and timestamps use UTC with fixed millisecond precision. Equal event data therefore produces the same canonical bytes.

SAY: Each device has its own chain. If somebody changes an old event, its recomputed hash no longer agrees. We do not force all devices through one global ordering point.

Important implementation details

The configured ingestion path uses w:1, which acknowledges the primary rather than a majority. Alerts and incident transactions use majority acknowledgement. This is a durability and throughput trade-off, not a promise of zero data loss during failover.

NOTE: Locks and chain-head caches belong to one API process. The current setup runs one ingestion process. Scaling to independent writers needs coordination or partitioning per device. The checker sorts by event time, so backdated events can also affect integrity interpretation.

7. How detection works
Rules are data stored in MongoDB

1. The detector watches inserts on the regular events collection using a MongoDB change stream.
2. It loads active rules and refreshes the cache through a second change stream on rules.
3. For an incoming event, it substitutes values such as {{srcIp}}, {{deviceId}}, {{ts}} or {{eventId}} into the stored pipeline.
4. It prepends the rule time window, executes aggregation on events with a time limit, and creates an alert when the pipeline returns a match.
5. It stores a resume token in system_state and uses dedupe/cooldown keys to reduce repeated alerts.

Rule type | Simple question
Windowed | Did too many suspicious activities happen within a time window?
Distinct | Did one source touch many different users or devices?
Sequence | Did failures happen before a success or command?
Baseline | Is recent traffic unusually high compared with telemetry history?
Allowlist | Is this client permitted to publish to this MQTT topic?

SAY: The detection condition is an aggregation pipeline stored in the rules collection. An administrator can change a rule without changing the detector program or redeploying the system.

Allowed stages include $match, $group, $project, $sort, $limit, $count, $addFields, $set and $unwind. Dangerous operators are checked recursively, including inside expressions. Stored rules cannot use $out, $merge, $function, $where, $accumulator or $lookup.

NOTE: The trusted chain-builder uses graph lookup separately. The rule editor is deliberately more restricted. Restart recovery also depends on the stored resume point remaining available in the replica-set oplog.

8. How incidents and risk are created
Graph relationships plus reliable related writes

Reconstruct the chain

The chain builder uses $graphLookup on alerts. It follows targetIp -> actor relationships, uses reverse traversal to find a starting point and includes related same-source findings. Time bounds, a depth limit and duplicate/cycle handling constrain the result. The application orders the returned evidence for display.

A -> B alert -> B -> C alert -> C -> D alert -> One ordered chain

Commit related data together

Transaction change | Why it must agree
Create or update incidents | The investigation contains the reconstructed chain
Set incidentId on related alerts | Evidence points to the correct investigation
Upsert risk_scores | Affected devices reflect the detection evidence

SAY: These changes happen in one multi-document transaction. Either they all commit or they all roll back. Snapshot reads provide a consistent transaction view, and majority acknowledgement is requested. Retrying the same chain must not create duplicate incidents.

Explain the risk formula without mathematics first

Recent severe alerts contribute more than old alerts. Contributions from the last 24 hours are added and capped at 100. With the default six-hour half-life, a severity-8 alert contributes about 8 now, 4 after six hours and 2 after twelve hours, when recalculated.

contribution = severity * exp(-lambda * ageHours)
lambda = ln(2) / halfLifeHours
risk = min(100, sum(contributions))

NOTE: MongoDB computes risk using aggregation, including $dateDiff and $exp. The API reads stored scores: they do not continuously decay on screen unless a calculation runs again. Time-series rollup writes stay outside the incident transaction.

SAY: The hash of an event depends on its contents and the previous hash. Editing a record changes its expected hash. Deleting a middle record breaks the link or sequence. Swapping timestamps changes the order used by the checker.

Why per-device chains?

Each device can be checked independently. The checker walks records in timestamp order and reports the first detected break for that device. It uses chainSeq as well as stored hash links to distinguish missing and reordered records.

Explain the limit honestly

A hash chain is tamper-evident, not tamper-proof and not a blockchain. A party with sufficient write access could rewrite hashes. Deleting the newest tail is only detectable against a separately trusted checkpoint. The checkpoint CLI can export anchors to system_state and an external JSON file; the dashboard Run check does not perform that external-anchor comparison.

NOTE: Old demo records can leave old failures in an all-device check. Identify the new demo IDs. TTL retention can remove chain prefixes, so retention expiry and unauthorized deletion require different operational interpretation.

18. DBMS features you can explain clearly
Name the database operation and its practical benefit

Feature | HoneyGraph use | Simple explanation
JSON Schema validation | Strict validators on events, rules and alerts | Reject invalid structure at the database boundary
Unique index | deviceId, IP, ruleId, username | Prevent duplicate identifiers
Compound index | events: deviceId+ts, srcIp+ts, eventType+ts; alerts: actor+ts | Find selected activity efficiently within a time range
Aggregation | Detection counts, distinct values, risk and summaries | Process matching documents inside MongoDB
Change streams | New events, rule changes, alert delivery | React to changes without repeated full-table polling
$graphLookup | Alert actor/target relationships | Follow connected records over several hops
Transactions | Incident + alert links + risk | Commit related collection changes together
2dsphere index | Device locations and radius queries | Use geographic distance rather than string matching
TTL | Configured events retention | Expire old data automatically in the background
Time-series collection | device_telemetry minute rollups | Store repeated time-based measurements efficiently

Indexes improve matching reads but consume storage and add write work. TTL is asynchronous; expiry is not guaranteed at the exact second. The current event retention default is seven days, configurable through environment settings.

NOTE: events stays a regular collection because the detector watches it and ingestion uses transactions. device_telemetry is time-series; it is not watched for event detection and its writes stay outside transactions. The rollup scheduler is a separate worker, not an always-running Compose service.

20. Normalization and relational mapping
Explain the design without calling MongoDB a relational database

Normalization reduces repeated facts and update problems in a relational design. Our implementation uses MongoDB collections, references and embedded data. The relational mapping below is a conceptual DBMS explanation of the same entities, not a set of SQL tables secretly used by the application.

Stage | Simple project explanation
Unnormalized (UNF) | One big report contains a device, its events, repeated alert lists and incident history in nested/repeating groups. Device facts appear many times.
First normal form (1NF) | In a relational view, move repeating lists into separate rows. Each relational cell holds one value. Keep events and alert-event links separately.
Second normal form (2NF) | For a relation with a composite key, non-key facts must depend on the whole key. Device firmware belongs to Device, not AlertEvent(alertId,eventId).
Third normal form (3NF) | Remove non-key-to-non-key dependencies: rule name/severity belong to Rule, and device type/IP belong to Device, referenced by their identifiers.

ER-to-relational mapping: main entities and links

Device(deviceId PK, ip UNIQUE, type, firmware, location)
Event(eventId PK, deviceId FK, ts, protocol, payload, hash)
Telemetry(telemetryId PK, deviceId FK, ts, eventCount, ...)
Rule(ruleId PK, name, stage, severity, pipeline, active)
Alert(alertId PK, ruleId FK, deviceId FK, incidentId FK, ...)
AlertEvent(alertId PK/FK, eventId PK/FK)
Incident(incidentId PK, status, createdAt, updatedAt)
IncidentStep(incidentId PK/FK, position PK, alertId FK)
StatusHistory(incidentId PK/FK, entryNo PK, status, ts, by)
RiskScore(deviceId PK/FK, score, calculatedAt)
RiskFactor(deviceId PK/FK, position PK, alertId FK, contribution)
AppUser(userId PK, username UNIQUE, passwordHash, role, active)

SAY: We separate reusable facts and use identifiers to reduce unnecessary repetition. In MongoDB, we also embed incident chain and history data because the detail screen reads them together. This is a deliberate document-modeling choice.

NOTE: PK/FK labels apply to this conceptual relational mapping. MongoDB references do not automatically enforce foreign-key constraints. Array fields in MongoDB are valid; they do not mean the MongoDB application must literally satisfy relational 1NF.

Replica set explanation

Three MongoDB nodes form rs0. Normally one primary accepts writes and two secondaries replicate data. If the primary becomes unavailable, an eligible secondary can be elected. keyFile authentication protects member-to-member access. Replication improves availability; it is not a backup or sharding.

rs.status().members.map(m => ({
  name: m.name, state: m.stateStr
}))

NOTE: Application analyst is not the same identity as MongoDB analyst. App status updates use api_svc permissions. All three nodes run on the same laptop, so losing the laptop still stops the demo. Ingestion is a trusted local demo endpoint; production exposure needs additional protection.

23. Simple viva answers
Use short answers, then point to the implementation

Question | Answer in simple language
Why MongoDB? | Different protocol payloads fit documents, and MongoDB supplies aggregation, streams, graph traversal and transactions. We still enforce schemas.
Why not only Python processing? | The DBMS project demonstrates native database computation. Python coordinates the queries and displays their results.
Event vs alert vs incident? | Event: activity. Alert: suspicious rule match. Incident: related alerts grouped into an investigation.
What is a change stream? | A database notification feed for changes such as inserts. The detector uses it rather than repeatedly scanning everything.
What does graph lookup do? | It recursively follows related alert actor/target IPs within defined time and depth bounds.
Where is ACID used? | Incident creation, alert linking and risk updates commit together. Snapshot reads and majority writes support the transaction.
Is it a blockchain? | No. It is a per-device SHA-256 hash chain, without distributed blockchain consensus.
Can you detect deletion of the latest log? | Only when a separately trusted checkpoint proves that the missing tail previously existed.
Why two kinds of time data? | events holds raw evidence; time-series device_telemetry holds per-minute summaries.
Are the graph links foreign keys? | They are application-managed MongoDB references. SQL foreign-key labels are only for the conceptual relational mapping.
Is analyst read-only? | The database analyst account is read-only. The application analyst can also triage incidents through the API.
What is the outcome? | An analyst can trace suspicious findings to events, inspect connected chains, prioritize devices and check log integrity.

SAY: The main learning is that a database can do more than store records. It can validate structure, react to changes, aggregate patterns, follow relationships and keep related writes consistent.
